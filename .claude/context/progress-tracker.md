## Completed

- **Background job for Cloudinary cleanup** — new `cloudinary_cleanup_jobs` table (`lib/db.ts`, migration `0012_nasty_wolfsbane.sql`): `publicId`, `status` (pending/done/failed), `attempts`, `lastError`. `lib/cloudinary-cleanup.ts` exports `enqueueCloudinaryCleanup` (inserts job rows synchronously, in the same request as the DB delete — durable even if nothing else ever runs), `runCleanupJobs` (attempts each job's `cloudinary.uploader.destroy` once, records success/failure, caps retries at 5 before marking `failed`), and `sweepPendingCloudinaryCleanup` (cron entry point — picks up jobs older than 2 minutes still `pending`, so it doesn't race an in-flight immediate attempt). `lib/actions/albums.ts`'s three delete actions now call `enqueueCloudinaryCleanup` before responding, then still fire the immediate best-effort attempt via `after()` (fast path for the common case — most deletes clean up right away); the DB job row is what guarantees the asset eventually gets cleaned up even if that `after()` call never runs. New `app/api/cron/cloudinary-cleanup/route.ts` (checks `Authorization: Bearer $CRON_SECRET` if that env var is set, no-ops open otherwise — same graceful-degradation pattern as `lib/rate-limit.ts`), scheduled via new `vercel.json` — once daily (`0 3 * * *`), not every 15 min: Vercel's Hobby plan caps cron jobs at once per day, and a `*/15 * * * *` schedule failed deployment with that exact error. ## Architecture Decisions

- **Widgets-per-row (`widgets` table), not one JSONB array per user** — moving one widget was rewriting every widget's data on every drag/resize. `widget_layouts` kept in place, unused, as a rollback source.
- **One root-level QueryClient, not one per dashboard mount** — a client created inside a page component gets torn down on every client-side route change, wiping the whole cache and forcing every widget to refetch everything.
- **`unwrapAction()` bridges `{error?: string}`-returning server actions into TanStack Query** — actions here return an error object instead of throwing; useMutation's onError/retry only fires on a real rejection, so every mutationFn/queryFn wraps its action call with this helper.
- **Cloudinary stays as the media store** (not migrating to Vercel Blob) — already CDN-backed, already wired through the whole upload path; only the transport (proxied vs. direct-to-cloud) needs to change, not the storage provider.
- **`useDraggable` tiles must not carry their own in-place `transform` when the drag target lies outside a scrolling ancestor** — the first drag-and-drop pass on photo tiles applied dnd-kit's `transform` directly to the tile's own inline style, so the moving thumbnail was clipped by the photo grid's `overflow-y-auto` container the moment it crossed toward the sidebar (same root cause the board's `DragOverlay` comment already documented, missed on the first pass here). Fix: the source tile only dims (`opacity`) during drag; a `DragOverlay` portalled to `document.body` (via `createPortal`, same pattern as `entry-board.tsx`) is the thing that actually renders the moving ghost, unaffected by any ancestor's overflow/transform.
- **`unstable_cache` must be re-wrapped inside the exported function body, not defined once at module scope, when tags need to vary per resource id** — `unstable_cache`'s `tags` option can't reference an argument if the wrapper is built at module load time. Re-constructing the wrapper on every call (closing over the already-resolved `id`/`organizationId`) is the documented, correct pattern — Next's cache key combines the wrapped function's source text with the `keyParts` array, so re-creating an identical closure each call still hits the same cache entry; it doesn't defeat caching.
- **`headers()`/`cookies()` (and anything that calls them, like `requireViewerContext()`) must run OUTSIDE `unstable_cache`** — those dynamic APIs throw if called from inside a cached function. Every cached read here resolves `viewer.organizationId` first, then passes it as a plain closed-over value into the cache wrapper.
- **`revalidateTag(tag)` with one argument is deprecated in Next 16** — the type signature now requires a second `profile` arg. Passing a named profile string (`"max"`, etc.) requires the `cacheComponents` config flag (unset here) to resolve; passing `{ expire: 0 }` instead reproduces the old immediate single-arg invalidation behavior without depending on that flag — confirmed by reading `revalidateTag`'s own source (`cacheLife?.expire === 0` is the exact condition that triggers the old "mark path revalidated" behavior).
- **Never branch which provider COMPONENT renders based on `typeof window`** — the persist-client setup initially rendered `QueryClientProvider` on the server and `PersistQueryClientProvider` on the client (different component tree shapes), which shifted every downstream `useId()`-based id (base-ui's `Checkbox`/`Menu`, etc.) and caused a hydration mismatch. Fix: always render the same provider; only the *storage backing* differs by environment (a no-op stub during SSR, real `localStorage` on the client).
