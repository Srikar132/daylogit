## Completed

- **Bug 1 — markdown not parsed (tables and every other element type)** — THREE separate causes, all now fixed and verified against a real `Editor` instance in `tests/markdown-editor.test.ts` (jsdom), using the exact table the user reported:
  1. **Blank lines between table rows.** The reported paste had every row separated by a blank line. A blank line terminates a table per GFM, so `marked`/`markdown-it` both parse it as a stack of pipe-filled paragraphs — and `@tiptap/extension-table`'s own `markdownTokenizer` explicitly cuts its candidate at `src.indexOf("\n\n")`, so it can't help either. `normalizeMarkdownSource()` (`lib/tiptap/markdown-signal.ts`) drops blank runs that sit BETWEEN two pipe rows and leaves every other blank line alone.
  2. **Double-parsing.** The first attempt called `parser.parse(md)` and handed the resulting HTML to `setContent`/`insertContent` — but `tiptap-markdown` overrides both commands to run `parser.parse()` themselves, and its `insertContentAt` override forces `{ inline: true }`, whose `normalizeInline` unwraps block structure. So the pre-parsed HTML got run through markdown-it a second time and came out flattened.
  3. **Wrong package.** Migrated off `tiptap-markdown@0.9.0` (community, markdown-it, HTML-string output, paste hook that only fires when the clipboard has no html flavour) to the OFFICIAL **`@tiptap/markdown@3.30.1`** — version-matched to our Tiptap 3.30, `marked`-based, and it returns ProseMirror JSON rather than an HTML string, so the double-parse trap doesn't exist. Parsing is now opt-in per call via `contentType: "markdown"`. `@tiptap/extension-table`/`-bold`/`-italic`/`-strike`/`-code`/`-link`/`-list`/`-horizontal-rule` all already ship `parseMarkdown`/`renderMarkdown` specs, so every element type maps without extra work, and `editor.getMarkdown()` now serializes back out. `tiptap-markdown` uninstalled.
- **Bug 1 (cont.) — what else changed:** `use-canvas-paste.ts`'s `textToMarkdownDoc` turned a pasted markdown string into one plain paragraph per line — no parsing at all, so a paste that landed on the canvas (rather than inside an already-open note) could never produce a table no matter what the editor supported. Pasted text is now handed to the new note as `{ pendingMarkdown: text }` (mirroring bookmark's `pendingUrl`) and `MarkdownWidget` consumes it on mount via `setContent(normalizeMarkdownSource(md), { contentType: "markdown" })` — parsing has to happen there because the widget's own extension set decides which nodes the markdown may produce. Also broadened the paste detector: the old `MARKDOWN_SIGNAL` only matched headings/fences/table rows, so pasted bold/italic/strikethrough/lists/links/task-lists/inline-code fell through to the raw-text path. Detection lives in `lib/tiptap/markdown-signal.ts` (`shouldParseAsMarkdown`, `looksLikeMarkdown`, `normalizeMarkdownSource`), unit-tested in `tests/markdown-signal.test.ts`. Rule for competing clipboard flavours: if `text/html` carries real formatting tags, ProseMirror's html path wins; if its only "rich" tag is a `<pre>`/`<code>` wrapper (the usual shape when copying a markdown code block out of a chat/docs page), the plain-text flavour is parsed as markdown instead. `markedOptions: { gfm: true, breaks: true }` in both editors keeps a single newline a hard break, so pasted multi-line text keeps the lines the user pasted.

## Architecture Decisions

- **Use the official `@tiptap/markdown`, not `tiptap-markdown`** — the community package returns an HTML string and overrides `setContent`/`insertContentAt` to parse markdown implicitly (the second with `inline: true`), which silently double-parses anything a caller pre-parsed and flattens block nodes. The official extension is version-locked to Tiptap, returns ProseMirror JSON, and only parses when a call passes `contentType: "markdown"` — explicit, single-pass, no trap.
- **Markdown paste needs a detector regardless of package** — `@tiptap/markdown` has NO paste handling: it parses only for explicit `contentType: "markdown"` callers, and ProseMirror's default paste path never passes that. `MarkdownPasteHandler` exists solely to decide when the clipboard's plain-text flavour is markdown source; parsing itself is entirely the official extension's.
- **Markdown source pasted onto the canvas is stored as `pendingMarkdown` and parsed by the note's own editor, never pre-parsed at the paste site** — the paste hook has no editor instance, so it cannot know which nodes are permitted; a doc built there can only ever be plain paragraphs. Same handoff shape as bookmark's `pendingUrl`.
- **Clipboard flavour arbitration for markdown paste** — real formatting tags in `text/html` mean ProseMirror's html path wins; a `<pre>`/`<code>`-only wrapper means the plain-text flavour is markdown source and gets parsed as such. Rationale: copying a fenced markdown block out of a chat or docs page is the most common way markdown source reaches these editors, and its only rich tag is the wrapper itself.
- **Document-level canvas listeners must check the event target** — the canvas paste hook is bound to `document`, so anything editable inside a widget would otherwise double-handle every paste. Guard on `defaultPrevented` plus an editable-target test.
